S3 仕組みの説明

今日作るエージェントの中で、何が起きているか

今日作るAIエージェントは、5つの技術を組み合わせて動いています。LLMを軸に、LLMだけではできなかったことを、次の技術が埋めてきました。この順に説明します。

  1. 2017年〜LLM　次の言葉を確率で選んで、文章を作る（2022年11月にChatGPTが公開）
  2. 2013年〜ベクトル検索　言葉を数の並びにして、意味の近さで探す（LLMより前からある技術。RAGでLLMと組み合わされた）
  3. 2020年RAG　検索で資料を探し、LLMに渡して答えさせる
  4. 2023年Function calling　LLMが「この関数を呼ぶ」と決める
  5. 2022年〜AIエージェント　目的に向かって、次に何をするかを自分で決めて動く（考え方は2022年。広く使われるようになったのはFunction callingのあと）

年は、その技術が論文や製品として広く知られるきっかけになった時期です。くわしくは、ページの最後の出典を見てください。

2017年〜

1LLM：次の言葉を確率で選ぶ

2017年に、今のLLMのもとになる仕組み（Transformer）が発表されました。2022年11月にChatGPTが公開されて、誰でも使えるものになりました。

LLMは、それまでの文章を読んで、次に来そうな言葉を候補ごとの確率で出します。その確率に従って1つ選び、また次の言葉を選びます。これをくり返して文章を作ります。いちばん確率の高い言葉が毎回選ばれるとは限らないので、同じ質問をしても、聞くたびに文面が変わります。

ためしてみる（数字は説明用のたとえです）

「42 Tokyoの魅力は、」の次に来る言葉の候補:

42 Tokyoの魅力は、…

次へ　LLMは、学習した知識の中から言葉を選びます。今日の合言葉や、皆さんが書くQAのように、学習していないことは知りません。知らないことも、もっともらしく答えてしまいます。そこで、外にある資料を探してくる技術が要ります。その技術は、LLMより前からありました。次のベクトル検索です。

2013年〜

2ベクトル検索：意味の近さで探す

コンピュータで文章を探すとき、もともとは「同じ言葉が入っているか」で探していました。それでは、「学費」で探しても「授業料」の文書は見つかりません。

2013年ごろから、言葉や文章を数の並び（ベクトル）に変える技術が広まりました。意味の近い文章は、ベクトルの向きが近くなります。向きの近さを点数にすれば、言葉が違っても意味の近いものを探せます。これがベクトル検索です。文章をベクトルに変えるのは、LLMとは別の専用のモデル（埋め込みモデル）です。今日使う埋め込みモデル（text-embedding-3-small）では、1つの文章が1536個の数になります。

ためしてみる（2次元に縮めたたとえです。本物は1536次元）

質問を選ぶと、QAとの近さの点数が出ます。言葉が一致していなくても、意味が近ければ点数は高くなります。

順位点数QAの質問

次へ　ベクトル検索は、意味の近い資料を見つけてくれます。でも、見つけるだけで、質問に答える文章は作れません。見つけた資料をLLMに渡せば、LLMが学習していないことでも、資料をもとに答えられます。この組み合わせが、次のRAGです。

2020年

3RAG：検索で資料を探し、LLMに渡して答えさせる

RAG（検索拡張生成）は、2020年に論文で発表された考え方です。質問が来たら、まずベクトル検索で関係しそうな資料を探し、その資料と質問をいっしょにLLMへ渡して答えさせます。LLMが学習していないことでも、資料に書いてあれば答えられるようになります。

LLMは、渡された資料だけで答えるとは限りません。もともと知っていることも混ぜて答えます。資料に書いていないことが、もっともらしく回答に入ることがあります。
Laboroの現場から

RAGの回答がおかしいとき、原因はLLMより検索の側にあることがよくあります。まず、答えに必要な資料が上位に引けているかを確かめます。資料が引けていなければ、LLMを替えても回答はよくなりません。

その先：引ける資料の質を上げる工夫

今日のRAGは、ベクトル検索で上位3件を引く、いちばん基本の形です。仕事では、次のような工夫を組み合わせて、引ける資料の質を上げます。

  • ハイブリッド検索　ベクトル検索の節で触れた「同じ言葉が入っているか」で探す検索と、ベクトル検索を組み合わせます。型番や固有名詞のように、言葉がそのまま一致してほしいものに強くなります。
  • リランキング　候補を多めに引いてから、質問との関係を別のモデルで読み直して並べ替えます。
  • Graph RAG　資料から「何と何がどう関係しているか」を取り出してグラフ（つながりの図）にし、そのつながりをたどって探します。「資料全体でよく出てくる話題は？」のように、1つの資料だけでは答えられない質問に向いています。2024年にMicrosoftの研究者が発表しました。
  • 検索をエージェントに任せる形　検索するか、何で検索するか、もう一度検索するかをLLMに決めさせます（Agentic RAGと呼ばれます）。今日作るのはこの形で、5番目のAIエージェントの節で説明します。

次へ　今日の基本の形のRAGは、質問が何であっても必ず先に検索します。「こんにちは」にも検索が走ります。検索するかどうかを、LLM自身が決められないからです。LLMに「このツールを使う」と決めさせる仕組みが、次のFunction callingです。

2023年

4Function calling：LLMが「この関数を呼ぶ」と決める

2023年6月に、OpenAIがAPIの機能としてFunction callingを発表しました。LLMに関数の説明を渡しておくと、LLMは質問を読んで「この関数を呼ぶ」と決め、関数に渡す引数を作ります。LLMに渡すこの関数を、ADKでは「ツール」と呼びます。ただし、LLMが関数を実行するわけではありません。実行するのはプログラム（今日はADK）で、LLMはその戻り値を読んでから答えます。

LLMは関数の中身のコードを読みません。読むのは、関数の名前、引数とその型、docstring（説明文）だけです。

たとえば、こんな関数を渡すと

def get_menu(day: str) -> dict:
    """指定した曜日の学食のメニューを返す。学食や昼ごはんについて聞かれたときに使う。

    Args:
        day: 曜日。「月」「火」のように1文字で渡す。
    """
    ...

LLMに見えているのは、これだけです

名前:   get_menu
説明:   指定した曜日の学食のメニューを返す。学食や昼ごはんについて聞かれたときに使う。
引数:   day（文字列）  曜日。「月」「火」のように1文字で渡す。

「火曜の学食は？」と聞かれると、LLMは get_menu(day="火") を呼ぶと決めます。「こんにちは」には呼びません。

説明文の書き方しだいで、関数は呼ばれたり呼ばれなかったりします。「何をする関数か」と「いつ使うか」を書いておくと、LLMが判断しやすくなります。
S6で使うコマンド　python try_tool.py で、つないだ関数がLLMにどう見えているかを確かめられます。python try_tool.py 関数名 引数 とすると、LLMを通さずに関数だけを呼んで、戻り値を見られます。うまく動かないときは、関数とLLMのどちらに原因があるかを、ここで切り分けてください。
Laboroの現場から

関数の名前と説明文は、LLMが読む仕様書です。関数が呼ばれないときは、プロンプトより先に説明文を見直します。人が読んで「いつ使うか」が分からない説明は、LLMにも伝わりません。

次へ　Function callingで、LLMはツールを使うかどうかを決められるようになりました。ただ、何を聞くか、次に何をさせるかを決めているのは、まだ使う人です。目的だけを渡せば、そこから先の手順をLLMが自分で決めて動く。それがAIエージェントです。

2022年〜

5AIエージェント：目的に向かって、次に何をするかを自分で決めて動く

LLMは、聞かれたことに1回答えるだけです。AIエージェントは、目的を渡されると、何をどの順でやるかを自分で決めて、目的を果たすまで動き続けます。

この「自分で決めて動く」こと（自律性）が、LLMとAIエージェントのいちばん大きな違いです。今日使うGoogleのADKは、エージェントを「特定の目的を果たすために自律的に動く実行単位」と説明しています。Anthropicも2024年12月の記事で、エージェントを「LLMが自分の進め方とツールの使い方を、その場で決めるシステム」とし、決められた手順を順にたどる仕組み（ワークフロー）と区別しています。

LLMAIエージェント
渡すもの1つの質問目的（今日なら「42 Tokyoの魅力を、QA集をもとに答える」役目）
次に何をするか使う人が決める（次の質問を考えるのは人）エージェントが自分で決める
外の世界学習したことだけで答えるツールで調べたり、動かしたりする
動く回数1回答えたら終わり目的を果たしたと判断するまで、決める・呼ぶ・読むをくり返す
RAGとの違い—RAGは「必ず先に検索する」という手順を人が決めている。エージェントは、検索するか、何で検索するか、もう一度検索するかを自分で決める

自律的に動くための部品

エージェントを作るときの部品は、判断するLLM、手足になるツール（Function calling）、決める・呼ぶ・読むのくり返しです。ただし、部品をそろえただけではエージェントとは言えません。分かれ目は、次に何をするかを決めているのが、人が書いた手順か、エージェント自身かです。

このくり返しの考え方は、2022年10月の論文（ReAct）で示されました。Function callingが広まってからは、エージェントを組み立てる仕組み（フレームワーク）が各社から出ています。今日使うADK（Agent Development Kit）も、その一つで、2025年4月に公開されました。

今日作るもの：検索をツールにしたエージェント

今日は、ベクトル検索を関数にして、エージェントのツールとして渡します。エージェントは、知らないことを聞かれたら自分で検索を呼び、見つかったQAをもとに答えます。「こんにちは」には検索せずに答えます。小さなエージェントですが、検索するかどうか、何という言葉で検索するかを、人が決めた手順ではなく、自分で決めています。

S6でやること　S5で試した検索を関数にして、エージェントにツールとして渡します。my_agent/agent.py のTODOと、ADKのドキュメントのツールのページを読んで、自分の手で書いてください。python ask.py では、「調べる → 引けた資料 → 回答」の3段で、エージェントの動きが毎回表示されます。
Laboroの現場から

エージェントは自分で手順を決めるので、同じ質問でも、どのツールをどう呼ぶかが毎回変わることがあります。仕事で作るときは、どこまでをエージェントに任せ、どこで人が確かめるかを先に決めます。回答がおかしいときは、どのツールが呼ばれ、何が引けていたかを最初に見ます。今日の ask.py は、これを毎回表示します。
